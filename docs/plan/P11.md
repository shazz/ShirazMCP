## 1. Deliverable in one sentence

Two new MCP tools (tool count 25 → 27): **`record_audio`** — record N real
seconds of the emulated ST's sound output to a WAV on disk via Hatari's
native recorder (fast-forward suspended for the window) and return a path
handle + format facts, and **`spectrogram`** — record (or reuse an existing
WAV) and return an STFT spectrogram PNG inline (magma colormap, parameters
matching the trusted STEIsNotDead pipeline) plus optional waveform PNG and
a compact JSON of the axes/energy facts, so an agent can *see* whether a
sound routine plays, what it plays, and how it changed after a `patch`.

### 2.1 Command vocabulary (from `/usr/share/hatari/hconsole/hconsole.py`, cross-checked against `strings /usr/bin/hatari`)

- `hatari-shortcut` tokens: `mousegrab, coldreset, warmreset, screenshot,
  bosskey, recanim, recsound, savemem` — **there is NO `fastforward`
  shortcut token in 2.4.1.** Fast-forward is controlled at runtime via
  `hatari-option --fast-forward on|off` (idempotent set, not a toggle —
  strictly better for us than a toggle would be).
- `hatari-path` tokens: `memauto, memsave, midiout, printout, soundout,
  rs232in, rs232out, sccbout` — `soundout` sets the sound-recording output
  file. Extension selects the format: `.wav` ⇒ WAV, `.ym` ⇒ YM register
  dump. We always use `.wav`.

### 2.2 The exact fifo lines and their log echoes (all verified live)

| Fifo line written | Log echo (verbatim, contains-match target in **bold**) |
|---|---|
| `hatari-path soundout /abs/file.wav` | `soundout: <old-path> -> /abs/file.wav` — match **`soundout: `** |
| `hatari-option --fast-forward off` | three lines: `Command line with '2' arguments:` / `- '--fast-forward'` / `- 'off'` — match **`- '--fast-forward'`** |
| `hatari-option --fast-forward on` | same three-line shape ending `- 'on'` — match **`- '--fast-forward'`** |
| `hatari-shortcut recsound` (start) | `INFO : WAV sound data recording has been started.` — match **`sound data recording has been started`** |
| `hatari-shortcut recsound` (stop) | `INFO : WAV Sound data recording has been stopped.` — match **`data recording has been stopped`** |

Pinned quirks, load-bearing:

- **`recsound` is a toggle** (start/stop alternate). The start and stop log
  lines differ in case (`sound` vs `Sound`) — the two distinct match
  strings above are chosen to be unambiguous per direction and immune to
  the case quirk.
- **`soundout` echoes even when the path is unchanged** (probed: setting
  the same path twice logs `soundout: X -> X` twice). Waiting for the echo
  is therefore always safe — it can never hang on a no-op.
- **`hatari-option` echoes even when the value is unchanged** (probed:
  `--fast-forward on` while already on still prints the `Command line
  with '2' arguments:` block). The *value* line (`- 'on'`) was observed to
  lag/truncate under process kill, so the match target is the *argument*
  line `- '--fast-forward'`, which appeared promptly in every probe.
  Successive waits cannot cross-match: `LogTail`'s cursor advances past
  each matched line.
- These are **control commands, not debugger commands** — no `hatari-debug`
  prefix, no sentinel round-trip (ADR-7 does not apply). Each has its own
  pinned log echo instead; that echo *is* the synchronization primitive.
- The default soundout path is relative to Hatari's cwd (probed:
  `hatari.wav` in an unrelated directory) — we must always set an absolute
  path before recording.

### 2.3 Fast-forward is fatal to recording quality (probed, quantitative)

Recording 3 wall-clock seconds of the MJJ demo:

| Fast-forward | WAV size | Audio duration in the file |
|---|---|---|
| **on** (our boot default) | 6 858 312 B | **38.88 s** (≈13× compressed garbage) |
| **off** | 528 656 B | **3.00 s** (exactly real time) |

Conclusion (contract): Hatari records at *emulated* time. The tool MUST
run the machine at real time for the record window — `--fast-forward off`
before starting, restore after. Recording N seconds therefore takes N real
seconds of wall-clock (the tool `sleep`s through it, session lock held).
A `WARN : Your system is too slow, some sound samples were not correctly
emulated` line may appear in the log around fast-forward transitions —
harmless, never matched by any of our contains-targets.

### 2.4 WAV format Hatari writes (probed, both recordings)

RIFF/WAVE, `fmt ` tag **1 (integer PCM)**, **44100 Hz** (the `--sound`
default — we don't pass the flag), **2 channels**, **16-bit** little-endian.
Real-time capture of the MJJ demo was fully non-silent (every sample
nonzero, peak ≈ 0.85 FS). The reader (§7.2) still takes rate/channels/width
from the header, never assumes.

## 3. The design decisions (ADR-22, §13)

1. **Reuse Hatari's native recorder** (`soundout` + `recsound`) instead of
   intercepting the emulator's audio device or resampling YM state
   ourselves: zero new emulation code, byte-exact what the user would hear,
   and the file lands on disk — a path handle, never bytes in context
   (ADR-5). Rejected: PulseAudio/pipewire loopback capture (fragile,
   host-config-dependent, breaks headless); `.ym` register capture (loses
   STE DMA/digidrums; still available later via the same seam).
2. **Real-time record window**: `hatari-option --fast-forward off` →
   record → restore. §2.3 makes anything else garbage. The session lock is
   deliberately held for the whole window — a concurrent freeze or memory
   read mid-recording would corrupt the capture; single-session semantics
   already serialize tools at the same lock.
3. **Log-echo synchronization, not sentinels**: control commands don't
   round-trip through the debugger; each has a pinned echo (§2.2) and a
   new narrow `HatariProcess::control_and_wait` primitive (§6.1) waits on
   it. No blind sleeps anywhere except the record window itself, which is
   the point.
4. **Rust-native DSP, parameters pinned to the trusted Python** (§7): Hann
   2048 / hop 512 / linear frequency axis to fmax 8000 Hz / magma / 80 dB
   range. Two deliberate, documented deviations from matplotlib: (a) the
   dB color range is pinned to [max−80, max] instead of matplotlib's
   data-dependent auto-range (determinism beats auto-contrast), and (b)
   color normalization is computed over the *displayed* bins (≤ fmax)
   rather than all bins (better contrast in the band the agent actually
   sees). Axes/labels/titles are not drawn (no font rendering); the JSON
   carries the axis mapping instead.
5. **New dependencies `hound` + `rustfft`** (§5) — the only two, both pure
   Rust, both pinned. A hand-rolled WAV parser and DFT were rejected as
   cognitive debt vs. two zero-transitive-dep, de-facto-standard crates.

/// Send a raw control command (`hatari-path`/`hatari-option`/
/// `hatari-shortcut`) over the fifo and wait until the log echoes
/// `expect` (P11 §2.2 — each control command has a pinned echo; there is
/// no debugger sentinel on this path, ADR-22). Collected lines are
/// discarded: the echo is a synchronization barrier, not output.
/// Fifo-plane only — callers must hold a Running session.
pub async fn control_and_wait(
    &mut self,
    line: &str,
    expect: &str,
    what: &str,
    timeout_ms: u64,
) -> Result<()> {
    self.write_wrapper(line).await?;
    let mut sink = Vec::new();
    self.log
        .read_until(|l| l.contains(expect), what, timeout_ms, &mut sink)
        .await
}
```

Nothing else in the file changes. *Implementation note:* the file is ~182
non-test lines today; this addition keeps it under 200 — verify in the §12
line audit; if it tips over, move `shutdown` into `spawn/control.rs`
(mechanical, no signature change) rather than shrinking this method.

```rust

/// Mono audio in [-1, 1] at `rate` Hz — the unit every DSP fn consumes.
#[derive(Debug, Clone, PartialEq)]
pub struct AudioBuf {
    pub samples: Vec<f32>,
    pub rate: u32,

/// Encode an RGB image as PNG bytes. Local twin of
/// `ripper::image::render::png_bytes` (which takes Rgba) — duplicated
/// rather than imported so `audio` stays a leaf with no `ripper` edge.
pub(crate) fn png_encode(img: &image::RgbImage) -> crate::error::Result<Vec<u8>> {
    let mut buf = Vec::new();
    img.write_to(
        &mut std::io::Cursor::new(&mut buf),
        image::ImageFormat::Png,
    )
    .map_err(|e| crate::error::Error::Parse {
        context: "png encode".to_string(),
        input: e.to_string(),
    })?;
    Ok(buf)
}
```

### 7.2 `src/audio/wav.rs` — reader (hound)

```rust
/// Format + level facts read from a WAV (wire-facing, plain data).
#[derive(Debug, Clone, PartialEq)]
pub struct WavInfo {
    pub sample_rate: u32,
    pub channels: u16,
    pub bits_per_sample: u16,
    pub duration_s: f64, // frames / rate
    pub peak: f32,       // max |sample| after mono mix, 0.0..=1.0
}

/// Read a PCM WAV → channel-averaged mono f32 in [-1, 1] + facts.
/// Matches STEIsNotDead `wavio.read_wav` semantics (mean of channels,
/// scale by 2^(bits-1)). Only integer PCM 16-bit is accepted — that is
/// what Hatari writes (§2.4); anything else is Error::Parse.
pub fn read_mono(path: &std::path::Path) -> Result<(AudioBuf, WavInfo)>
```

Exact behavior:

1. `hound::WavReader::open(path)` — error ⇒ `Error::Parse { context:
   "wav read", input: e.to_string() }`.
2. `let spec = reader.spec();` accept only `spec.sample_format ==
   hound::SampleFormat::Int && spec.bits_per_sample == 16`; else
   `Error::Parse { context: "wav format", input: format!("{spec:?}") }`.
3. Collect `reader.samples::<i16>()` into `Vec<i16>` (any per-sample
   decode error ⇒ `Error::Parse { context: "wav samples", .. }`).
4. Mono mix: for each frame (chunk of `channels` samples), `mean of
   (s as f32 / 32768.0)`. A trailing partial frame (malformed file) is
   dropped silently (`chunks_exact`).
5. `peak = samples.iter().fold(0f32, |m, s| m.max(s.abs()))`;
   `duration_s = frames as f64 / rate as f64`.
6. An empty WAV (0 frames) is NOT an error here — `render` (§7.4) rejects
   short input with context; the tool layer converts to invalid_params.

```rust
/// The rendered spectrogram + the axis facts the wire layer reports.
#[derive(Debug)]
pub struct SpecImage {
    pub png: Vec<u8>,
    pub width: u32,     // frames * scale_x
    pub height: u32,    // bins * scale_y
    pub frames: usize,
    pub bins: usize,    // rows kept, bin 0 ..= fmax
    pub scale_x: u32,
    pub scale_y: u32,
    pub fmax_hz: u32,   // effective (clamped) value actually rendered

/// Symmetric Hann, numpy `np.hanning(N)` exactly:
/// w[i] = 0.5 - 0.5*cos(2*pi*i / (N-1)).
fn hann(n: usize) -> Vec<f32>

/// Magnitude STFT: frames x (N_FFT/2 + 1). Frame f covers samples
/// [f*HOP, f*HOP + N_FFT); frame count = (len - N_FFT)/HOP + 1.
/// Err(Parse{context:"stft input"}) when len < N_FFT.
fn stft_mag(samples: &[f32]) -> Result<Vec<Vec<f32>>>

/// mag relative to `max` → LUT index. 0 dB → 255, ≤ -80 dB → 0, linear
/// between: round(((db + 80) / 80) * 255). `max <= 0` (silence) → 0.
fn db_index(mag: f32, max: f32) -> u8

/// The whole pipeline. `fmax_hz` is clamped to 500 ..= rate/2 before
/// use (the clamped value is returned in `SpecImage::fmax_hz`).
pub fn render(audio: &AudioBuf, fmax_hz: u32) -> Result<SpecImage>
```

Exact math (no deviation):

1. **STFT** — plan one `rustfft::FftPlanner::<f32>::new()
   .plan_fft_forward(N_FFT)` and reuse it for all frames. Per frame:
   `buf[i] = Complex { re: samples[f*HOP + i] * win[i], im: 0.0 }`,
   `fft.process(&mut buf)`, magnitude of bins `0..=N_FFT/2` =
   `(re*re + im*im).sqrt()`. (rustfft is unnormalized, same as `np.fft.rfft`
   — no scaling factor anywhere.)
2. **Kept bins** — `bins = min(N_FFT/2 + 1, (fmax_hz as u64 * N_FFT as u64
   / audio.rate as u64) as usize + 1)`. For 8000 Hz @ 44100: **372**.
3. **Normalization** — `max` = the maximum magnitude over ALL frames but
   only the KEPT bins (deviation (b) of §3.4, deliberate). If `max <= 0.0`
   every pixel is `MAGMA[0]` (silent recording still renders).
4. **dB → index** — `db = 20.0 * (mag / max + 1e-12).log10()`, clamp to
   `[-DB_RANGE, 0.0]`, `idx = ((db + DB_RANGE) / DB_RANGE * 255.0).round()
   as u8`.
5. **Orientation** — column x = frame x (time left→right); row y = bin
   `bins - 1 - (y / scale_y)` (frequency: **top row = fmax, bottom row =
   0 Hz** — same visual orientation as the matplotlib renders).
6. **Integer upscale (nearest-neighbor)** — `scale_x = max(1,
   MIN_W.div_ceil(frames))`, `scale_y = max(1, MIN_H.div_ceil(bins))`;
   final raster `frames*scale_x × bins*scale_y`, each source pixel
   replicated. (A 1 s recording: 83 frames → scale_x 8 → 664 px wide;
   372 bins → scale_y 1 → 372 px tall. A 30 s recording: 2582 frames →
   scale_x 1.) No smoothing, no font/axes.
7. Build an `image::RgbImage`, encode via `super::png_encode`.

Split into helpers (`fn hann`, `fn stft_mag`, `fn db_index`,
`fn keep_bins`, `fn paint`) to respect the 30-line ceiling.

### 8.2 The choreography

```rust
/// Record `seconds` of real-time audio to `wav_path` (absolute, .wav —
/// validated by the caller). Returns whether fast-forward was suspended
/// and restored (true iff the session config boots with it on).
///
/// Sequence (each step = control_and_wait with the §8.1 mark,
/// config.sentinel_timeout_ms):
///   1. soundout_cmd(wav_path)          → SOUNDOUT_MARK
///   2. ff_cmd(false)  [if config.fast_forward] → FF_MARK
///   3. RECSOUND_CMD                    → REC_STARTED_MARK
///   4. tokio::time::sleep(seconds)     — the real-time window (§2.3)
///   5. RECSOUND_CMD                    → REC_STOPPED_MARK
///   6. ff_cmd(true)   [if config.fast_forward] → FF_MARK
/// Error precedence mirrors ADR-20: a record-window error (3-5) wins
/// over a restore error (6); restore is still attempted after a window
/// failure.
pub async fn record_wav(
    proc: &mut HatariProcess,
    seconds: f64,
    wav_path: &std::path::Path,
) -> Result<bool> {
    let t = proc.config().sentinel_timeout_ms;
    let ff = proc.config().fast_forward;
    proc.control_and_wait(&soundout_cmd(wav_path), SOUNDOUT_MARK, "soundout path change", t)
        .await?;
    if ff {
        proc.control_and_wait(&ff_cmd(false), FF_MARK, "fast-forward off", t)
            .await?;
    }
    let window = run_window(proc, seconds, t).await;
    let restore = if ff {
        proc.control_and_wait(&ff_cmd(true), FF_MARK, "fast-forward on", t)
            .await
    } else {
        Ok(())
    };
    window.and(restore).map(|()| ff)
}

async fn run_window(proc: &mut HatariProcess, seconds: f64, t: u64) -> Result<()> {
    proc.control_and_wait(RECSOUND_CMD, REC_STARTED_MARK, "sound recording start", t)
        .await?;
    tokio::time::sleep(std::time::Duration::from_secs_f64(seconds)).await;
    proc.control_and_wait(RECSOUND_CMD, REC_STOPPED_MARK, "sound recording stop", t)
        .await
}
```

Failure semantics, exact:

- Step 1 or 2 fails → propagate; nothing to clean up (recording never
  started; a stale fast-forward-off after a step-2 *timeout* is
  impossible — the timeout means the fifo/log path is broken and the
  session is effectively dead; `stop`/`start` recovers).
- Step 3 fails → `run_window` returns the error before sleeping; restore
  (6) still runs (the `window.and(restore)` shape above does exactly
  this ordering).
- Step 5 fails (start succeeded, stop echo never seen) → the recording
  may still be armed inside Hatari. **Known limitation, documented in
  ADR-22:** the error is returned (window error wins), fast-forward is
  restored, and the agent's remedy is `stop`/`start` (a `recsound` retry
  would toggle blind). Never observed live; the stop echo landed < 100 ms
  after the command in every probe.
- The caller holds the session lock throughout — the sleep in step 4 is
  the documented real-time cost (§2.3), not a blind synchronization sleep
  (ADR-7 is about *synchronization*; this sleep *is* the product).

## 10. `src/tools/audio.rs` — the tools

Header: `//! P11 audio tools: record_audio (Hatari native WAV recorder,
real-time window — session::record) and spectrogram (pure DSP over the
WAV — crate::audio). Thin adapters; the wire layer is audio_wire.rs.`

### 10.1 Shared recording entry

```rust
impl HatariServer {
    /// Validate + resolve the path, then drive session::record::record_wav
    /// under the session lock. Requires Running (a frozen CPU produces no
    /// audio and does not service the fifo). Lock is held for the whole
    /// window — deliberate, §3.2/ADR-22.
    async fn record_to(
        &self,
        seconds: f64,
        path_arg: Option<&str>,
    ) -> Result<(std::path::PathBuf, bool), McpError> {
        let seconds = validate_seconds(seconds).map_err(|m| McpError::invalid_params(m, None))?;
        let mut guard = self.session.lock().await;
        let wav_path = match path_arg {
            Some(p) => validate_wav_out(p).map_err(|m| McpError::invalid_params(m, None))?,
            None => {
                let n = self.audio_seq.fetch_add(1, Ordering::Relaxed) + 1;
                guard.config().work_dir.join(format!("audio-{n:04}.wav"))
            }
        };
        let proc = match &mut *guard {
            AnySession::Running(s) => s.process_mut(),
            other => return Err(wrong_state(other.state_name(), "running")),
        };
        let restored = crate::session::record::record_wav(proc, seconds, &wav_path)
            .await
            .map_err(to_mcp)?;
        Ok((wav_path, restored))
    }
}
```

*Implementation note:* if `AnySession` field/method names differ slightly
(e.g. config access), follow the exact pattern used by `tools/rip.rs`'s
session access — copy, don't invent. For a user-supplied `path`, after
`validate_wav_out` and before calling `record_wav`, also verify the
parent directory exists (`tokio::fs::metadata(parent)`; missing ⇒
invalid_params `"parent directory does not exist: …"`) — Hatari fails
silently on unwritable soundout paths.

### 10.2 `record_audio`

```rust
// `vis = "pub(crate)"`: see lifecycle.rs for the rationale (rmcp-2.2 gotcha).
#[tool_router(router = audio_router, vis = "pub(crate)")]
impl HatariServer {
    #[tool(
        name = "record_audio",
        description = "Record the emulated Atari ST's sound output to a \
WAV file using Hatari's native recorder. Fast-forward is suspended so the \
capture is real-time: recording N seconds blocks for N real seconds (max \

    )]
    pub async fn record_audio(
        &self,
        Parameters(a): Parameters<RecordAudioArgs>,
    ) -> Result<Json<RecordAudioOutput>, McpError> {
        let (wav_path, restored) = self.record_to(a.seconds, a.path.as_deref()).await?;
        let (buf, info) = crate::audio::wav::read_mono(&wav_path).map_err(to_mcp)?;
        drop(buf);
        Ok(Json(RecordAudioOutput {
            wav_path: wav_path.display().to_string(),
            sample_rate: info.sample_rate,
            channels: info.channels,
            bits_per_sample: info.bits_per_sample,

```

(`read_mono` runs synchronously on a ≤ 5.3 MB file — milliseconds; the

### 10.3 `spectrogram`

```rust
    #[tool(
        name = "spectrogram",
        description = "See the music: STFT spectrogram of the ST's sound \
output, returned inline as a PNG (magma colormap; time left-to-right, \
0 Hz at the bottom, fmax_hz at the top, 80 dB color range) plus a JSON \
with the axis mapping (px_per_second, hz_per_row) and a peak/silent \
verdict. Give seconds (0.5-30) to record first — real-time, blocks for \
that long, requires a running session — or wav_path to analyze an \

adds an amplitude-envelope PNG. Ideal for before/after comparison around \
a patch to a sound routine."
    )]
    pub async fn spectrogram(
        &self,
        Parameters(a): Parameters<SpectrogramArgs>,
    ) -> Result<CallToolResult, McpError>
```

Exact behavior:

1. `validate_source(&a)` ⇒ invalid_params on violation. `include_waveform
   = a.include_waveform.unwrap_or(false)`.
2. `SpecSource::Record(s)` → `let (wav_path, _) = self.record_to(s,
   None).await?;` (recorded spectrogram input always goes to the default
   work-dir name — a custom WAV location is `record_audio`'s job).
   `SpecSource::Wav(p)` → verify the file exists
   (`tokio::fs::metadata`; missing ⇒ invalid_params) and its length is
   ≤ 64 MiB (guard against decoding an arbitrary giant file into memory;
   larger ⇒ invalid_params `"wav too large (> 64 MiB)"`). **No session
   access on this arm** — do not take the lock.
3. `let (buf, info) = crate::audio::wav::read_mono(&wav_path).map_err(to_mcp)?;`
4. `let spec = crate::audio::spectrogram::render(&buf,
   a.fmax_hz.unwrap_or(FMAX_DEFAULT_HZ)).map_err(to_mcp)?;` — a
   too-short recording (< 2048 samples ≈ 46 ms) surfaces as
   `Error::Parse` → `to_mcp`; unreachable via the `seconds` arm
   (min 0.5 s), reachable via a degenerate `wav_path`.
5. Artifact files, named from ONE sequence draw `let n =
   self.audio_seq.fetch_add(1, Ordering::Relaxed) + 1;`:
   `spectrogram-{n:04}.png` (always) and `waveform-{n:04}.png` (iff
   `include_waveform`), written to `work_dir` via `tokio::fs::write`
   (map errors through `to_mcp(Error::Io(e))`). The waveform render is
   `crate::audio::waveform::render(&buf.samples)`. Read `work_dir` from
   the server config the same way `tools/view.rs` does.
6. `build_spec_output(..)` with `peak = info.peak`, `silent = info.peak <
   SILENT_PEAK`.
7. Blocks, in this order (contractual): `ContentBlock::image(b64_spec,
   "image/png")` — base64 STANDARD engine exactly like view.rs; then, iff
   `include_waveform`, `ContentBlock::image(b64_wave, "image/png")`; then
   `ContentBlock::text(serde_json::to_string(&out)…)` (serialize-error
   mapping copied from extract.rs's `out_json`). Return
   `CallToolResult::success(blocks)`.

Split steps 5–7 into a `fn compose`/`async fn write_artifacts` pair as
needed for the 30-line ceiling.

### 10.4 Token-efficiency invariants (ADR-5 — checked in review)

- Audio samples NEVER appear in any text/JSON block — WAV is a path
  handle; the spectrogram/waveform are image blocks + path handles.
- Default `spectrogram` call = ONE image + ONE compact JSON text block.
- The recording is resumable state on disk: an agent can `record_audio`
  once and `spectrogram(wav_path=…)` many times (different fmax, with/
  without waveform) without touching the emulator again.

## 13. ADR-22 — append to decisions.md (template, verbatim)

```markdown
## 2026-07-XX — ADR-22: Audio capture via Hatari's native recorder + Rust-native spectrogram

**Status:** accepted
**Context:** Agents verifying sound routines (or comparing before/after a
`patch`) had no way to observe the ST's audio output — screenshots show
the screen, nothing showed the speaker. shazz already trusts a Python
spectrogram pipeline (STEIsNotDead tools/audio: matplotlib specgram
NFFT=2048/noverlap=1536/Hanning/magma, fmax 8000, channel-mean mono mix)
whose renders he can read fluently.
**Decision:** Two tools. `record_audio` drives Hatari 2.4.1's built-in
sound recorder over the control fifo: `hatari-path soundout <abs.wav>` →
`hatari-option --fast-forward off` → `hatari-shortcut recsound` → real-
time sleep → `recsound` → `--fast-forward on`. Every command is confirmed
by a live-pinned log echo (control commands have no debugger sentinel;
the echo IS the sync primitive — soundout and hatari-option echo even on
no-op, verified live). Fast-forward MUST be suspended: Hatari records
emulated time (probed: 3 wall-seconds under fast-forward yielded 38.9 s
of ~13x-compressed garbage; real-time yielded exactly 3.00 s), and 2.4.1
has no `fastforward` shortcut token, so `hatari-option` (an idempotent
set, better than a toggle) is the mechanism. The session lock is held for
the whole window — a concurrent freeze mid-recording would corrupt the
capture. `spectrogram` reimplements the trusted pipeline Rust-native
(hound + rustfft; embedded 256-entry magma LUT): Hann 2048, hop 512,
linear axis to fmax (default 8000 Hz), 80 dB color range pinned to the
max (deviation from matplotlib's auto-range, for determinism), normalized
over displayed bins only. The DSP lives in `src/audio/`, a pure leaf —
unit-tested with synthesized sines (bin-exact assertions), zero emulator
involvement. Token efficiency (ADR-5): WAV = path handle, spectrogram =
inline PNG + compact JSON axis facts; `spectrogram(wav_path=…)`
re-analyzes an existing recording in any session state without touching
the emulator.
**Alternatives considered:** (a) host-side audio loopback capture
(PulseAudio/pipewire) — host-config-dependent, breaks headless, races the
mixer; (b) `.ym` register capture + our own YM synthesis — loses STE DMA
sound and digidrums, large new emulation surface (still open as a later
plugin via the same soundout seam); (c) shelling to the existing Python —
new runtime dependency, violates self-containment; (d) `realfft`/colormap
crates — two more deps for marginal gain over rustfft + a const LUT.
**Consequences:** Recording N seconds blocks the (single) session for N
real seconds — the one deliberate long sleep in the codebase (it is the
product, not a synchronization hack; ADR-7 unaffected). New deps: hound
3.5.x, rustfft 6.4.x (pure Rust, lockfile-pinned). A stop-echo timeout
mid-recording can leave Hatari's recorder armed (never observed live);
remedy is stop/start — a blind recsound retry would toggle the wrong way.
The recorder captures Hatari's final mixed output (YM + STE DMA +
crossbar), sample-exact at the configured --sound rate (default 44100),
2-ch 16-bit PCM (probed). HatariProcess gained one narrow primitive,
`control_and_wait` (raw control command + log-echo barrier).
```
