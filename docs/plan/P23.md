control transport behind an adapter so the crate compiles everywhere (Phase

Hatari on Windows (Phase B: the hrdb fork's RDB TCP protocol — see §3, the

## 1. Deliverable in one sentence (Phase A)

All Hatari control I/O moves behind a `ControlTransport` trait in
`src/session/transport/` — the existing FIFO/stdin/sentinel machinery becomes
its `#[cfg(unix)]` `FifoTransport` impl, byte-for-byte behavior-identical —
so `cargo check --target x86_64-pc-windows-msvc` succeeds (non-Unix `start`
returns a clear `Error::Unsupported`), proven by the moved unit suite, a new
trait-contract suite over a `FakeTransport`, a new hermetic fake-Hatari
integration test of spawn/boot/debug/freeze/thaw, and new CI jobs (Windows
cross-check + windows-latest test + release artifact).

## 3. Research finding: how Hatari can be controlled on Windows — the honest answer

Verified against the local Hatari source tree (`$HOME/projects/hatari`,
which is `github.com/tattlemuss/hatari` — the **hrdb fork**, `git describe`:
`hrdb-v0.010-2-gf7f659d0`, based on mainline Hatari 2.6.1 per
`readme.txt`/`version.h`) and against mainline's repo listing.

### 3.1 Stock (mainline) Hatari on Windows has NO external command channel. Full stop.

- The *entire* external-control implementation is compiled under
  `#if HAVE_UNIX_DOMAIN_SOCKETS` (`src/control.c:13,407`), which CMake sets
  only if `sys/socket.h` + `sys/un.h` exist (`CMakeLists.txt:229`) — false on
  MinGW/MSVC Windows builds.
- On such builds, `--cmd-fifo` and `--control-socket` are not even registered
  as options (`src/options.c:525-529` under the same `#if`), and the control
  functions are preprocessor stubs returning error strings
  (`src/includes/control.h:22-25`: *"Command FIFO is not supported on this
  platform."*).
- The `--control-socket` variant would not help anyway: it is `AF_UNIX`, and
  Hatari is the *client* connecting to a path we would listen on
  (`control.c:571-602`).
- The stdin/DebugUI plane alone cannot substitute: DebugUI reads stdin only
  once the CPU is parked, and **there is no remote way to park it** without a
  control channel (only the SDL keyboard shortcut or `--debug` at boot).
  Worse, Windows Hatari with the console window enabled rebinds stdin to a
  freshly allocated console (`src/gui-win/opencon.c`: `AllocConsole()` +
  `freopen("CON","r",stdin)`), discarding any pipe we passed.
- Mainline (github.com/hatari/hatari `src/debug/`, checked 2026-07-11) has
  **no** `remotedebug.c` — the RDB channel below is fork-only.

Any spec that claimed "just use a named pipe / just use the control socket on
Windows" would be fiction. There is no Phase B against stock Hatari.

### 3.2 The realistic Windows path: the hrdb fork's RDB TCP server (this is what the local checkout is)

The tattlemuss fork — the de-facto "remote-debuggable Hatari", with Windows
binaries shipped for its hrdb debugger — adds `src/debug/remotedebug.c`:

| Property | Pinned at |
|---|---|
| Always-on TCP server (started unconditionally from `main()`) | `main.c:864` (`RemoteDebug_Init`), polled per-VBL `main.c:592` |
| **Loopback only**, fixed port **56001**, one client (`listen(...,1)`) | `remotedebug.c:59` (`RDB_PORT`), `:1839-1841` (`INADDR_LOOPBACK`), `:1856` |
| **Works on Windows by design**: winsock init, `__WINDOWS__` paths | `remotedebug.c:27-29` (`HAVE_WINSOCK_SOCKETS`, `CMakeLists.txt:230`), `:1932-1945` (`WSAStartup`) |
| Framing: commands are `NUL`-terminated strings; responses `NUL`-terminated with `0x01` field separators; out-of-band notifications prefixed `!` (e.g. `!status`) | `remotedebug.c:95` (`SEPARATOR_VAL`), `:1602-1626` (`RemoteDebug_ProcessBuffer`), `:229-271` (`send_str`/`send_sep`/`send_term`), `:331` |
| Protocol version handshake value `0x1009` | `remotedebug.c:91` (`REMOTEDEBUG_PROTOCOL_ID`) |
| Verbs: `status break step run regs mem memset bp bplist bpdel symlist exmask console setstd infoym profile resetwarm resetcold ffwd memfind savebin dmem histset histget` | `remotedebug.c:1383-1412` (command table) |
| `console <line>` = full DebugUI console passthrough (`DebugUI_ParseConsoleCommand`), with console output redirected to a file registered via `setstd` (on Windows it `freopen`s stdout to that file) | `remotedebug.c:983-1003`, `:419-459` |
| `break` requests debugger entry from *outside* (the thing stock Hatari cannot do); `run` resumes | `remotedebug.c` command table + `RemoteDebug_CheckRemoteBreak` (`:1977-1988`) |

**Consequence for ShirazMCP:** Windows support (Phase B) means an
`RdbTransport` speaking this TCP protocol, and requires users to run an
hrdb-fork Hatari build on Windows (they already must, for any remote-debug
workflow there). Bonus: TCP is cross-platform, so `RdbTransport` is
developable and CI-testable **on Linux** against the fork — no Windows
hardware needed to build Phase B.

### 3.3 Cross-platform-socket vs FIFO on Unix — recommendation

Do **not** unify on the RDB socket now. The FIFO transport works against
*stock/distro* Hatari (`/usr/bin/hatari`, mainline 2.x) — unifying would
force every Unix user onto the fork for zero functional gain today. Decision:
FIFO stays the Unix default; `RdbTransport` (Phase B) is the only Windows
transport and an *opt-in* on Unix (which is exactly how we test it). Revisit
unification only if mainline Hatari ever merges a remote-control channel.
This is recorded in the ADR (§8.2).

## 4. Design: the `ControlTransport` adapter

### 4.1 Altitude — one whole strategy per transport

The trait sits at the **session-ops level** (the current `HatariProcess`
method surface), *not* at the wire level ("write a line to the FIFO"). A
wire-level trait cannot host RDB: RDB has framed responses over the socket
(no sentinels, no log-tail sync), a native `break` verb (no armed-breakpoint
freeze dance), and no stdin plane at all. So each impl owns its entire
strategy — planes, sync, freeze protocol — and the trait promises only the
operations the session layer and tools actually consume.

### 4.2 Dispatch — enum, not `Box<dyn>`, not a generic on `Session<S>`

- The trait uses native async-fn-in-trait, which is not dyn-compatible; we
  will not add an `async_trait`/boxing dependency for a closed set of 2 real
  impls + 1 stub + 1 test fake. A **`Transport` enum** dispatches; the enum
  itself implements the trait so `HatariProcess` delegation is one line per
  method.
- Making `Session<S, C: ControlTransport>` generic would infect
  `state.rs::SessionState::Data`, `AnySession`, and every tool signature —
  rejected as accidental complexity. `HatariProcess`'s public surface is
  unchanged; nothing above `session/` knows transports exist.
- Transports are **not cargo features**: selection is platform `cfg` +
  (Phase B) runtime config. The default build on every OS keeps compiling
  and passing tests — the additive-only property holds trivially.
- Transport *establishment* (arg contribution + boot gate) stays **inherent
  per impl**, not on the trait — constructors legitimately differ in shape
  (`FifoTransport` needs the child's stdin; `RdbTransport` will need a
  connect/retry loop) and are selected at compile/spawn time anyway.

### 4.3 The trait (write exactly this, in `src/session/transport/mod.rs`)

```rust
use crate::error::Result;

/// One complete strategy for controlling a live Hatari process (ADR-39):
/// how commands reach the emulator, how completion is detected, and how the
/// Running↔Paused control planes work. Impls own the whole story; the
/// session layer promises to call `freeze`/`thaw`/`continue_until_break`
/// only in the orders the `Session<S>` type-state permits.
pub(crate) trait ControlTransport: Send + Sync + std::fmt::Debug {
    /// Sentinel-/protocol-synced debugger command; returns the command's
    /// output with transport protocol lines stripped (ADR-7 semantics).
    async fn debug_with_timeout(&mut self, cmd: &str, timeout_ms: u64) -> Result<String>;

    /// Raw wrapper/control command on the running-plane channel — no
    /// completion sync (callers confirm liveness separately, §5.6 of P1).
    async fn write_wrapper(&mut self, line: &str) -> Result<()>;

    /// Wrapper command, then block until the log echoes `expect` (ADR-23's
    /// pinned-echo barrier). Running-plane only.
    async fn control_and_wait(
        &mut self,
        line: &str,
        expect: &str,
        what: &str,
        timeout_ms: u64,
    ) -> Result<()>;

    /// Park the CPU (the Running→Paused half of ADR-11). On `Ok` the frozen
    /// control plane is live and drained.
    async fn freeze(&mut self) -> Result<()>;

    /// Resume (Paused→Running). On `Ok` the running plane is confirmed live.
    async fn thaw(&mut self) -> Result<()>;

    /// From frozen: run until a breakpoint fires (frozen again on `Ok`,
    /// running on `Err(Timeout)` — ADR-15 / `RunToBreak` contract).
    async fn continue_until_break(&mut self, timeout_ms: u64) -> Result<String>;

    /// Await a log line containing `needle` (state-load completion, §3.6).
    async fn wait_for_log(&mut self, needle: &str, timeout_ms: u64) -> Result<()>;

    /// Best-effort graceful-quit request (thaw-if-frozen + quit verb).
    /// Process reaping stays with `HatariProcess::shutdown`.
    async fn request_quit(&mut self) -> Result<()>;
}
```

`Sync` is required because `SessionState::Data: Send + Sync`
(`state.rs:16`). AFIT `Send`-future bounds need no `trait_variant`
machinery: every await site is on the concrete enum, never on a spawned
generic.

### 4.4 The dispatch enum (same file, or `dispatch.rs` if `mod.rs` nears 200)

```rust
#[derive(Debug)]
pub(crate) enum Transport {
    #[cfg(unix)]
    Fifo(fifo::FifoTransport),
    /// Never constructed in Phase A (spawn fails first); exists so dispatch
    /// compiles on non-Unix targets until RdbTransport (Phase B) lands.
    #[cfg(not(unix))]
    Unsupported(unsupported::Unsupported),
}

impl ControlTransport for Transport {
    async fn debug_with_timeout(&mut self, cmd: &str, timeout_ms: u64) -> Result<String> {
        match self {
            #[cfg(unix)]
            Transport::Fifo(t) => t.debug_with_timeout(cmd, timeout_ms).await,
            #[cfg(not(unix))]
            Transport::Unsupported(t) => t.debug_with_timeout(cmd, timeout_ms).await,
        }
    }
    // …identical match-delegation for the other seven methods…
}
```

`unsupported::Unsupported` is a unit struct whose every method returns:

```rust
Error::Unsupported {
    what: "live Hatari control on this platform (P23 Phase B adds the \
           RDB TCP transport for the hrdb Hatari fork)"
        .to_string(),
}
```

If `cargo check --target x86_64-pc-windows-msvc` flags the variant as never
constructed, annotate it
`#[cfg_attr(not(test), expect(dead_code, reason = "[P23] constructed only by tests until Phase B"))]`
and add a `#[cfg(all(test, not(unix)))]` test that constructs it and asserts
`Error::Unsupported` from each method (that test runs on the windows-latest
CI job, §7.5).

### 5.3 `request_quit` — carve out of today's `shutdown`

Today's `shutdown` (`spawn/control.rs:179-198`) mixes transport work
(thaw-if-frozen, write `hatari-shortcut quit`) with process work (2 s wait,
SIGKILL). Split exactly there:

- `FifoTransport::request_quit` (in `lifecycle.rs`): if
  `ControlChannel::DebugStdin`, write `c` on stdin (warn on failure, don't
  bail) and flip to `Fifo`; then `write_wrapper("hatari-shortcut quit")`.
  Returns the write error if the quit write fails (caller logs it).
- `HatariProcess::shutdown` (stays in `spawn/mod.rs`): call
  `self.transport.request_quit().await` (warn on `Err`), then the existing
  2 s `child.wait()` / `kill()` tail verbatim. Still never returns `Err`
  (P0 §7.2 contract).

## 6. What Windows gets in Phase A (say this in the release notes)

The MCP server binary builds and runs on Windows: handshake, tool listing,
and every tool that operates on **files** (depackers, disk/bootsector
extraction, MemImage analysis, audio rendering) works. `start` (and anything
needing a live session) returns the `Unsupported` error with the Phase B
pointer. That is the milestone: compiling + honest, not pretending.

### 7.3 Hermetic fake-Hatari integration test (`tests/transport_fifo.rs`, `#![cfg(unix)]`)

New file. Proves the refactor preserved the **whole** spawn → boot-gate →
debug → freeze → thaw → shutdown pipeline without an emulator, using a bash
fake written to a tempdir (mode `0o755` via `std::os::unix::fs::PermissionsExt`)
and passed as `config.hatari_path`:

```bash
#!/usr/bin/env bash
# Fake Hatari for transport tests: creates the FIFO itself (mirrors
# control.c Control_SetFifo), answers every sentinel `evaluate $dead____`
# on either plane with the echo line Hatari would print, exits on quit.
set -u
fifo="" prev=""
for a in "$@"; do [ "$prev" = "--cmd-fifo" ] && fifo="$a"; prev="$a"; done
[ -n "$fifo" ] || exit 1
mkfifo "$fifo" || exit 1
answer() {
  case "$1" in
    *'evaluate $dead'*) printf '= %%0 (bin), #0 (dec), $%s (hex)\n' "${1##*evaluate \$}" ;;
  esac
}
# Frozen plane: DebugUI reads stdin.
while IFS= read -r line; do answer "$line"; done <&0 &
# Running plane: blocks here until the server opens the write end.
exec 3<"$fifo"
while IFS= read -r line <&3; do
  case "$line" in "hatari-shortcut quit") exit 0 ;; *) answer "$line" ;; esac
done
```

Tests (each with `work_dir` = its own tempdir; `boot_timeout_ms` and
`sentinel_timeout_ms` = 5000):

1. `spawn_boot_gate_and_debug`: `HatariProcess::spawn` succeeds (FIFO wait +
   write-end open + `evaluate pc` boot sentinel all exercised); then
   `proc.debug("evaluate pc").await` returns `Ok` (empty after
   protocol-stripping); then `proc.shutdown().await` — the script's exit on
   `hatari-shortcut quit` proves `request_quit` reaches the fifo.
2. `freeze_thaw_roundtrip`: after spawn, `proc.freeze().await` is `Ok`
   (ARM on fifo is ignored by the fake; the stdin confirm + drain sentinels
   are answered by the stdin loop), then `proc.thaw().await` is `Ok` (the
   `c` is ignored; fifo confirm answered). This makes ADR-11's freeze/thaw
   protocol hermetically regression-tested for the first time.
3. `spawn_fails_when_binary_missing` already exists at `session/mod.rs:127`
   — leave it; it now also covers the `kill_on_err` path post-refactor.

```markdown
## 2026-07-XX — ADR-39: Control transport is a platform adapter; Windows control requires the hrdb fork's RDB TCP channel

**Status:** accepted (Phase A shipped; Phase B — RdbTransport — pending)
**Context:** The crate did not compile on Windows: Hatari control ran over a
Unix FIFO (`--cmd-fifo`) plus `std::os::unix::fs::FileTypeExt`, so releases
shipped Linux/macOS only. Source audit of Hatari 2.6.1 (`control.c`,
`options.c`, `includes/control.h`): the entire external-control surface is
`#if HAVE_UNIX_DOMAIN_SOCKETS` — on Windows builds `--cmd-fifo`/
`--control-socket` are not registered and the functions are stubs returning
"not supported"; DebugUI's stdin is unreachable remotely (nothing can park
the CPU from outside, and gui-win/opencon.c rebinds stdin to a fresh
console). **Stock Hatari on Windows has no external command channel.** The
tattlemuss/hatari fork (hrdb) adds `debug/remotedebug.c`: an always-on TCP
server (loopback:56001, winsock-capable, protocol 0x1009) with structured
verbs (`break`/`run`/`mem`/`savebin`/…) and a `console` DebugUI passthrough
— the only realistic remote-control mechanism that exists on Windows.
**Decision:** Extract a session-ops-level `ControlTransport` trait
(`session/transport/`); today's fifo/stdin/sentinel machinery becomes its
`#[cfg(unix)]` `FifoTransport` impl, dispatched through a `Transport` enum
(AFIT, no boxing dep). Non-Unix builds compile and run the server;
`spawn` returns the new `Error::Unsupported` until Phase B lands
`RdbTransport` (tokio TCP, both platforms, targeting the fork's RDB
protocol). `Error::Fifo` is renamed `Error::Transport`.
**Alternatives considered:** (a) WSL-only Windows story — rejected: display/
audio friction, and it dodges rather than answers the port question;
(b) patch mainline Hatari's control.c with a winsock/TCP channel and ship
our own emulator build — rejected: we would own an emulator fork when a
maintained one already exists and is the de-facto Windows remote-debug
Hatari; (c) drive everything over stdin — impossible (no remote debugger
entry); (d) hand `--cmd-fifo` a Windows named pipe — impossible (Hatari
`mkfifo()`s the path itself, and the code is compiled out); (e) unify on
the RDB socket on every OS now — rejected: it would force Unix users off
stock/distro Hatari; fifo stays the Unix default, revisit if mainline ever
merges remote control.
**Consequences:** Crate + server build on all three OSes; Windows Phase A
artifact is "offline tools only" and says so. Windows live control will
require an hrdb-fork Hatari (≥ protocol 0x1009); fixed port 56001 means one
RDB Hatari per machine and a conflict with a running hrdb GUI; the socket is
loopback-only and unauthenticated — the same local-trust model as the
user-writable fifo. RdbTransport is Unix-testable, so the Windows transport
gets Linux CI coverage. Transport dispatch is a closed enum by design —
adding a transport is one module + one variant + one spawn arm.
```

## 9. Phase B — `RdbTransport` (spec'd here, gated; implement as its own phase after live verification)

Phase B is **not** part of Phase A's PR. It ships when P22 has released the
emulator and the §9.4 checklist is verified against a live fork build. Its
shape is pinned now so Phase A's seams are provably sufficient.

### 9.1 Scope

- `src/session/transport/rdb/` implementing `ControlTransport` over
  `tokio::net::TcpStream` to `127.0.0.1:56001` (add `"net"` to the tokio
  features — the only manifest change; no new crates).
- Compiled on **all** platforms (it is plain TCP) — this is what makes it
  Linux-CI-testable; it becomes the only *working* transport on Windows and
  an opt-in on Unix.
- `HatariConfig` gains `transport: TransportKind`
  (`enum TransportKind { Fifo, Rdb }`, default `Fifo` on unix, `Rdb`
  elsewhere) and the `start` tool gains an optional `transport` string
  param; `spawn` selects the `Transport` variant from it.
- Boot gate: spawn Hatari, then a bounded connect-retry loop (the server
  socket opens early in `main()`), then a `status` round-trip replaces the
  `evaluate pc` sentinel.

### 9.2 Protocol facts to build against (pinned, §3.2)

Requests: command string + `\0`. Responses: `\0`-terminated, `0x01` field
separators, first token `OK`/`NG`. Out-of-band notifications are frames
starting with `!` (`!status`, config/symbol notifications) and can arrive
between a request and its response — the read loop must demux: stash `!`
frames (latest-status cell), return the first non-`!` frame as the response.

### 9.3 Operation mapping (the trait holds — verified against the fork's command table)

| `ControlTransport` op | RDB realization |
|---|---|
| `debug_with_timeout(cmd)` | `console <cmd>` → `OK` frame; command *output* is read from the `setstd`-registered file tailed by a `LogTail` (lifted to `transport/log_tail.rs` in this phase) — deterministic: the fork `fflush`es before replying (`remotedebug.c:995`) |
| `write_wrapper(line)` | `console` equivalents (`hatari-option X` → `console setopt X`; `hatari-shortcut quit` → `console quit`) — table the handful of wrapper verbs actually used (`grep write_wrapper\|control_and_wait src/`) |
| `control_and_wait` | as above + existing log-echo barrier on the Hatari log file (unchanged — stdout/stderr redirect works on Windows) |
| `freeze` | `break` verb, then await the `!status` notification showing stopped; no ARM-breakpoint dance, no stdin plane at all |
| `thaw` | `run` verb + `!status` running |
| `continue_until_break` | `run`, then await the next stopped `!status` (bounded) |
| `wait_for_log` | `LogTail` on the Hatari log file, as today |
| `request_quit` | `console quit` (fallback: drop connection + process kill path) |

Where a mapping is richer natively (`mem`, `savebin`, `regs` beat
`console m` for bulk reads), do **not** exploit it in Phase B — parity
first; native-verb acceleration is a separate, later phase so behavior
stays comparable across transports.
